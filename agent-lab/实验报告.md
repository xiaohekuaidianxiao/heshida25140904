# 实验报告：基于 ReAct 智能体与 angr 的自动化逆向分析

---

## 1. 实验概述

### 1.1 背景

传统符号执行在面对含有死循环等复杂控制流的程序时，容易遭遇路径爆炸，且难以利用高层业务语义指导搜索。大语言模型（LLM）擅长语义理解与任务分解，却难以保证微观代码层面的严密性。本实验将 **ReAct（Reasoning + Acting）架构**应用于逆向分析场景，以 LLM 为决策与编排层，以 **angr** 为可调用工具，通过「思考—行动—观察」闭环，引导符号执行探索目标路径，完成对给定 crackme 的输入求解。

### 1.2 目标

- 封装至少两个 angr 工具供 Agent 调用
- 实现 ReAct 主循环，完成 LLM 与工具之间的闭环交互
- 求解 crackme 程序的正确输入

## 3. 目标程序分析

### 3.1 `crackme.c` 源码

修正原始代码中的笔误（`gadget trap` → `gadget_trap`，`check_password=password` → `check_password(password)`）后：

```c
#include <stdio.h>
#include <string.h>

void gadget_trap(void) {
    printf("Oops! You are trapped in a dead loop.\n");
    while (1) {
    }
}

int check_password(char *input) {
    if (strlen(input) < 4) {
        puts("Wrong password!");
        return 0;
    }
    if (input[0] == 'A') {
        if (input[1] == 'B') {
            gadget_trap();
        }
        if (input[1] == 'Z') {
            if ((input[2] ^ 0x12) == 'q') {
                if ((input[3] + 3) == 'H') {
                    puts("Success! Flag is found.");
                    return 1;
                }
            }
        }
    }
    puts("Wrong password!");
    return 0;
}

int main(void) {
    char password[10];
    printf("Enter password: ");
    scanf("%9s", password);
    check_password(password);
    return 0;
}
```

### 3.2 编译

```bash
gcc -no-pie crackme.c -o crackme
```

使用 `-no-pie` 禁用地址随机化，确保 angr 分析时地址固定。

### 3.3 程序逻辑分析

程序读取最多 9 字符的输入，经 `check_password` 函数逐层校验：

| 校验层   | 条件                         | 结果                           |
| ----- | -------------------------- | ---------------------------- |
| 第 1 层 | `strlen(input) < 4`        | 长度不足 → Wrong                 |
| 第 2 层 | `input[0] == 'A'`          | 不满足 → Wrong                  |
| 第 3 层 | `input[1] == 'B'`          | 进入 `gadget_trap()` **死循环**   |
| 第 4 层 | `input[1] == 'Z'`          | 不满足 → Wrong                  |
| 第 5 层 | `(input[2] ^ 0x12) == 'q'` | 不满足 → Wrong                  |
| 第 6 层 | `(input[3] + 3) == 'H'`    | 不满足 → Wrong；满足 → **Success** |

**逆推正确输入：**

```
input[0] = 'A'                          → 0x41
input[1] = 'Z'                          → 0x5A
input[2] = 'q' ^ 0x12 = 0x71 ^ 0x12    → 0x63 = 'c'
input[3] = 'H' - 3   = 0x48 - 0x03     → 0x45 = 'E'
```

**正确输入：`AZcE`**

### 3.4 关键地址（通过 angr CFG 分析获取）

| 含义                          | 地址         |
| --------------------------- | ---------- |
| `gadget_trap` 函数入口（avoid）   | `0x401156` |
| 输出 `"Success!"` 前的基本块（find） | `0x4011eb` |

## 4. 任务一：angr 工具封装

### 4.1 工具设计说明

封装了两个可被 Agent 调用的原子工具：

#### 工具 1：`controlled_explore`（受控路径探索）

```python
def controlled_explore(binary_path, find_addrs, avoid_addrs, max_steps=100) -> dict
```

- **功能**：在指定的 `find` / `avoid` 地址约束下，驱动 `SimulationManager` 探索程序路径
- **参数**：
  - `find_addrs`：目标地址列表（如 Success 输出的基本块地址）
  - `avoid_addrs`：需要避开的地址列表（如 `gadget_trap` 入口，避免死循环路径爆炸）
  - `max_steps`：`explore` 的最大步数上限
- **返回**：结构化字典，包含 `found`、`active`、`avoided`、`deadended`、`errored` 等路径统计，以及 `reached_target` 布尔标志
- **设计合理性**：使用 angr 的 `explore(find=..., avoid=...)` 参数，将 LLM 提供的语义理解转化为具体的地址约束，直接缩减符号执行的搜索空间

#### 工具 2：`solve_input`（输入求解）

```python
def solve_input(binary_path, find_addrs, avoid_addrs, max_steps=100) -> dict
```

- **功能**：探索到目标状态后，从 stdin 的符号约束中求解具体输入值
- **返回**：`success`、`input_ascii`、`input_hex`、`raw_hex` 等字段
- **设计合理性**：先复用 `explore` 到达成功状态，再调用 angr 的约束求解引擎（Z3）一次性求解所有符号字节，无需逐字符暴力搜索

### 4.2 工具调用关系

```
controlled_explore  →  确认路径可达，返回路径统计
         ↓（如果 reached_target = true）
solve_input         →  从 found 状态求解具体输入
```

## 5. 任务二：ReAct 主循环

### 5.1 架构设计

```
┌──────────────────────────────┐
│       LLM 决策层              │  Thought: 分析状态，决定下一步
├──────────────────────────────┤
│       解析/派发层              │  Action: 将 LLM 输出转为工具调用
├──────────────────────────────┤
│       angr 工具执行层          │  Observation: 返回结构化状态
└──────────────────────────────┘
```

### 5.2 目标与约束的显式描述

在系统提示词中明确告知 LLM：

- **目标**：倾向到达含 `"Success!"` 的输出路径
- **约束**：尽量避免进入与 `gadget_trap` / 死循环相关的路径（通过 `avoid` 地址实现）
- **策略**：分三步执行——先初步探索，再路径验证，最后输入求解

### 5.3 LLM 输出解析与派发

使用正则表达式从 LLM 输出中提取 `Thought` 和 `Action` 字段，将 `Action` 值映射到对应的工具函数进行调用。若 LLM 输出了无效工具名，返回纠正提示引导下一轮正确调用。

### 5.4 Observation 的构造

将 angr 执行后的关键状态整理为结构化 JSON 文本，包含：

- 路径统计（`found`、`active`、`deadended` 等计数）
- 目标是否可达（`reached_target`）
- 求解结果（`input_ascii`、`input_hex`）

## 7. 思考题

### 在本实验中，LLM 主要承担什么角色？它如何借助语义与常识，缓解纯符号执行在搜索空间上的困难？

LLM 在本实验中承担 **决策编排层（Orchestrator）** 的角色，具体体现在以下四个方面：

**（1）语义理解**

LLM 能理解程序的业务逻辑——"输入以 AZ 开头进入 Success 路径，以 AB 开头进入死循环"。这是纯符号执行做不到的，符号执行只看到地址和约束，不理解程序含义。

**（2）搜索空间裁剪**

基于语义理解，LLM 在系统提示中指定了 `avoid` 死循环地址、`find` 成功地址，将 angr 的搜索空间从全部路径缩减为目标路径，直接避免了路径爆炸问题。本实验中 `gadget_trap` 内含 `while(1)` 死循环，若不指定 `avoid` 地址，angr 会持续展开该路径直至资源耗尽。

**（3）策略规划**

LLM 通过 ReAct 循环分步执行——先 `controlled_explore` 确认路径可达，再验证稳定性，最后 `solve_input` 求解输入——而不是让 angr 盲目一次性搜索全部路径。这种「先探索、再验证、后求解」的策略体现了 LLM 的任务分解能力。

**（4）常识利用**

LLM 可以根据对程序结构的常识判断哪些分支值得探索、哪些应该跳过，这弥补了符号执行缺乏高层语义的短板。例如，LLM 从路径统计中推理出"found=1 且两次结果一致说明路径稳定可达"，这种高层推理是 angr 本身不具备的。
