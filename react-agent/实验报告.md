# 实验报告：ReAct Agent 静态二进制分析

---

## 一、实验背景与目的

本实验实现了一个基于 **ReAct（Reasoning + Acting）** 模式的智能体，由 LLM 负责推理与任务编排，将 **radare2** 与 **Ghidra** 作为可调用的静态分析工具，对目标二进制文件 `targets/challenge`（黑盒 ELF，已 strip，无源码）进行自动化漏洞挖掘。Agent 遵循 `Thought → Action → Observation` 的闭环推理模式，最终输出结构化的漏洞结论。

---

| 项目     | 配置                                         |

## 三、系统设计

### 3.1 工具封装

Agent 提供两类共 10 个可调用工具：

**radare2 工具（6 个）：**

- `r2_get_functions_info`：获取函数列表
- `r2_disassemble_function`：反汇编指定函数
- `r2_decompile_function`：获取伪 C 代码（pdc）
- `r2_search_strings`：搜索字符串
- `r2_get_imports`：获取导入函数
- `r2_get_xrefs_to`：获取地址交叉引用

**Ghidra 工具（4 个）：**

- `ghidra_decompile_function`：高质量反编译（DecompileFunc.java）
- `ghidra_get_function_calls`：函数内部调用关系（FuncCalls.java）
- `ghidra_get_cross_references`：函数交叉引用（FuncXrefs.java）
- `ghidra_vuln_scan`：自动扫描危险函数调用模式（VulnScan.java）

其中 `VulnScan.java` 为自研脚本，自动遍历全程序识别 24 类危险函数调用（如 fgets、strcpy、system 等），对每个调用点标记 `[INPUT]` 或 `[SINK]`，并输出前后 ±8 条指令上下文，危险调用指令用 `>>>` 高亮。

### 3.2 分析流程

采用两阶段架构：

- **第一阶段（VulnScan 预扫描）**：在 LLM 介入前，先用 Ghidra 自动扫描全程序的危险函数调用，将扫描结果注入 LLM 上下文，使 Agent 从一开始就能聚焦到正确的地址范围。
- **第二阶段（LLM 驱动的 ReAct 循环）**：LLM 根据预扫描结果，自主选择工具进行深度分析，追踪数据流路径，最终输出漏洞结论。

## 四、分析过程

以下为 Agent 实际运行的 ReAct 推理轨迹摘要（完整日志见 `logs/run.txt`）：

### Round 1：VulnScan 预扫描结果

VulnScan 自动发现 **5 个函数中共 6 个危险调用**：

| 函数                          | 调用地址       | 目标函数           | 标记    |
| --------------------------- | ---------- | -------------- | ----- |
| `__snprintf_chk @ 0x4010b0` | `0x4010b4` | __snprintf_chk | SINK  |
| `fgets @ 0x401100`          | `0x401104` | fgets          | INPUT |
| `__strcpy_chk @ 0x401120`   | `0x401124` | __strcpy_chk   | SINK  |
| `FUN_00401216 @ 0x401216`   | `0x401247` | __snprintf_chk | SINK  |
| `FUN_00401264 @ 0x401264`   | `0x40131b` | fgets          | INPUT |
| `FUN_00401264 @ 0x401264`   | `0x401382` | __strcpy_chk   | SINK  |

其中 `FUN_00401264`（即 r2 识别的 `main`）同时包含 INPUT 和 SINK，是数据流分析的核心关注对象。

### Round 2：获取函数列表

通过 radare2 获取函数列表，确认 `main @ 0x401264` 存在 7 个基本块、293 字节大小，以及辅助函数 `fcn.00401216 @ 0x401216`。

### Round 3：反编译 main 函数

通过 Ghidra 反编译 `FUN_00401264`，获取到完整的伪 C 代码，关键发现：

1. **栈帧大小**：`rsp -= 0xa0`（160 字节）
2. **fgets 调用**：`fgets(rsp+0x20, 0x80, stdin)` —— 将 stdin 数据读入 `rsp+32` 处的 128 字节缓冲区
3. **长度检查**：`strlen` 结果减 1 后与 `0x63`（99）比较，仅当 `strlen-1 <= 99` 时才继续
4. **__strcpy_chk 调用**：`__strcpy_chk(rsp, rsp+0x20, 0x10)` —— 将源缓冲区复制到 `rsp` 处，目标对象大小仅 16 字节

### Round 4-5：补充分析

通过 radare2 反汇编 `main` 获取完整的控制流图（含彩色标注的 CFG），通过反编译 `fcn.00401216` 确认其为日志输出函数（调用 `__snprintf_chk` 格式化 `[%s] %s` 后通过 `fputs` 输出到 stdout），与漏洞分析无直接关联。

### Round 6-7：辅助分析与最终结论

通过 r2 搜索字符串确认 `"profile-service ready"`、`"selftest"` 等程序语义，进一步理解程序功能。最终在 Round 7 中 Agent 综合所有证据，输出 Final Answer。

## 五、分析结果

### 5.1 漏洞结论

```json
{
  "vuln_type": "stack buffer overflow",
  "location": "main (0x00401264)",
  "cause": "函数通过fgets读取用户输入到栈缓冲区s1（位于rsp+0x20，大小0x80字节）。随后进行边界检查：计算输入字符串长度（strlen）并减去1，然后与99比较，若长度<=100则允许复制。然而，复制操作使用__strcpy_chk将源缓冲区s1（最大可含100字节）复制到目标缓冲区（位于rsp，大小仅为0x10字节）。由于检查未考虑目标缓冲区大小，允许远超目标容量的数据被复制，导致栈缓冲区溢出。"
}
```

### 5.2 漏洞分析详解

**漏洞类型**：栈缓冲区溢出（Stack Buffer Overflow）

**数据流路径**：

```
stdin
  │
  ▼
fgets(rsp+0x20, 0x80, stdin)    ← 读入最多 127 字节到 128 字节源缓冲区
  │
  ▼
strcspn() + strlen()            ← 去除换行符
  │
  ▼
检查: strlen(input)-1 <= 99     ← 长度检查：允许最多 100 字节
  │
  ▼
__strcpy_chk(rsp, rsp+0x20, 0x10) ← 复制到 16 字节目标缓冲区
```

**根因**：长度检查（允许 ≤100 字节）与目标缓冲区大小（仅 16 字节）严重不匹配。攻击者可输入 17~100 字节的数据，通过长度检查但溢出目标栈缓冲区，覆盖返回地址等关键栈数据。

**关键指令地址**：

- 读入操作：`0x40131b`（call fgets）
- 长度检查：`0x40134a`（cmp rax, 0x63）
- 溢出写入：`0x401382`（call __strcpy_chk）

### 5.3 二进制安全属性

| 属性           | 状态      | 说明               |
| ------------ | ------- | ---------------- |
| NX (DEP)     | ✅ 开启    | 栈不可执行，但可利用 ROP   |
| Stack Canary | ❌ 未启用   | 无栈保护，溢出可直接覆盖返回地址 |
| PIE          | ❌ 未启用   | 地址固定，便于构造利用      |
| RELRO        | Partial | GOT 可写           |

## 六、日志与结果一致性说明

`logs/run.txt` 记录了完整的 7 轮 ReAct 交互过程，包含所有 Thought、Action 和 Observation：

1. **VulnScan 预扫描**（Round 1）：输出了 `FUN_00401264` 中 `0x40131b`（fgets/INPUT）和 `0x401382`（__strcpy_chk/SINK）两个关键调用点及 ±8 条指令上下文——与 `vuln.json` 中的地址一致。

2. **r2 函数列表**（Round 2）：确认 `main @ 0x401264` 的存在及大小——与 `vuln.json` 中的函数名一致。

3. **r2 伪代码**（Round 3）：展示 `fgets(rsp+0x20, 0x80, stdin)`、`strlen` 检查（`cmp rax, 0x63`）、`__strcpy_chk(rsp, rbx, 0x10)` 的完整逻辑——与 `vuln.json` 中描述的数据流路径完全吻合。

4. **Ghidra 反编译**（Round 4）：该调因 Ghidra 脚本编译异常未能返回反编译结果，Agent 随后改用 radare2 补充，体现了 ReAct 模式的容错与自适应能力。

`vuln.json` 中的所有字段均可从日志中的工具输出直接推导得出，不存在手工编造或与日志矛盾的内容。

## 七、总结

本实验通过实现 ReAct Agent 成功完成了对 `challenge` 二进制文件的自动化静态漏洞分析。Agent 结合 VulnScan 预扫描定位可疑点、radare2 反汇编/反编译获取指令级细节、Ghidra 提供函数级上下文信息，在 7 轮交互中识别出 `main` 函数中的栈缓冲区溢出漏洞。该漏洞源于长度检查（≤100 字节）与目标缓冲区大小（16 字节）的严重不匹配，攻击者可输入 17~100 字节数据触发栈溢出。
